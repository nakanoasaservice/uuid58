# Roadmap: Specification and Multi-Language Support

A plan to grow uuid58 from a JavaScript library into a specification with
implementations in several languages.

## Principles

- **The specification and its test vectors are the source of truth.** The
  JavaScript package becomes the first implementation of the spec.
- Test vectors are generated by an **independent reference implementation**
  (plain integer arithmetic in Python), not by the JavaScript package, so that
  bugs in the JavaScript code cannot leak into the spec.
- Every implementation runs a conformance test that loads the same test
  vectors.

## Decisions

| Topic | Decision |
|---|---|
| Hyphens in encoder input | The spec is strict: only `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx` and 32 hex digits are valid. JavaScript 1.x keeps its current lenient behavior (it strips every hyphen, at any position and in any number) for compatibility, and the spec lists this as a known deviation. JavaScript 2.0 will follow the spec. |
| Location of the JavaScript package | Move it to `js/`. Its release tags become `js/v…`. |
| First target languages | Go, Python, Rust, Java/Kotlin |
| Generation (`uuid58()`) | Out of scope for the spec. The spec covers encoding, decoding, and validation only. Implementations may offer a UUIDv4 generator as an optional extra. |

## What the Spec Must Define

Taken from the current JavaScript behavior.

- **Operations**: defined as "16 bytes (an unsigned 128-bit integer,
  big-endian) ⇄ a 22-character Base58 string". Handling of UUID strings is
  layered on top.
- **Alphabet**: `123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz`
  (Bitcoin-compatible).
- **Encoding**
  - Input is either the 36-character hyphenated form or 32 hex digits.
  - Hex digits are case-insensitive.
  - Output is always 22 characters, left-padded with `1`.
- **Decoding**
  - Input must be exactly 22 characters. It is case-sensitive, and whitespace
    is not trimmed.
  - Values of 2^128 or more are an error.
  - Output is the 36-character lowercase hyphenated form.
- **Boundary values**
  - nil UUID ⇄ `1111111111111111111111`
  - max `ffffffff-ffff-ffff-ffff-ffffffffffff` ⇄ `YcVfxkQb6JRzqk5kF2tNLv`
- **Ordering guarantee**: the alphabet is in ascending ASCII order and the
  length is fixed, so comparing two encoded strings gives the same order as
  comparing their numeric values. (`isUuid58` already relies on this when it
  checks `<= MAX`.)
- **Errors**: the spec defines error kinds only. Messages are up to each
  implementation.
  - Encoding: `invalid_length`, `invalid_character`
  - Decoding: `invalid_length`, `invalid_character`, `overflow`
  - Implementations may measure string length differently (UTF-16 code units,
    bytes, or code points). Any input containing non-ASCII characters is an
    error under every measure, so the result is the same.
- **Validation (`isUuid58`)**: exactly 22 characters, only alphabet
  characters, and a value that fits in 128 bits.

## Phases

### Phase 1: Specification

Add `spec/` at the repository root. This does not depend on where the
JavaScript package lives, so it can go before Phase 2.

- [ ] `spec/SPEC.md`: uses RFC 2119 keywords and carries a version number.
      Covers everything in "What the Spec Must Define".
- [ ] `spec/vectors.json`
  - Valid pairs: nil, max, random values, uppercase input, input without
    hyphens
  - Invalid encoder inputs, each with its expected error kind
  - Invalid decoder inputs, each with its expected error kind (wrong length,
    `0OIl`, non-ASCII characters, overflow)
  - Inputs that only JavaScript 1.x accepts are marked `lenient`
- [ ] `spec/generate_vectors.py`: generates the vectors from the independent
      reference implementation
- [ ] JavaScript conformance test: loads `vectors.json` and checks every case
      (skipping `lenient` cases on 1.x)

### Phase 2: Repository Layout

- [ ] Move the JavaScript package into `js/` (package.json, vite.config.ts,
      tsconfig.json, bench/, tests, mise.toml, pnpm files)
- [ ] Split CI into one job per language, filtered by path. Changes under
      `spec/` run every language's job.
- [ ] Make the release workflows use per-language tags (`js/v…`, `go/v…`,
      `python/v…`, `rust/v…`, `java/v…`)
  - Update the check in `publish.yml` that compares the tag with the version
    in package.json to use the `js/v…` form
- [ ] Split the README into a repository overview and one README per language

### Phase 3: Four Implementations

After Phase 2 the languages are independent of each other and can be built in
parallel. Each one is done when it has:

- all test vectors passing
- a README
- everything ready to publish to its registry (check that the package name is
  available before starting)

| Language | Location | Registry | 128-bit handling / native UUID type |
|---|---|---|---|
| Go | `go/` (module `github.com/nakanoasaservice/uuid58/go`) | Go modules | two `uint64`s / `[16]byte` |
| Python | `python/` | PyPI | `int` / `uuid.UUID` |
| Rust | `rust/` | crates.io | `u128` / the `uuid` crate behind a feature flag |
| Java/Kotlin | `java/` | Maven Central | two `long`s / `java.util.UUID`. Kotlin uses the Java library; add extension functions if needed. |

### Phase 4: JavaScript 2.0

- [ ] Make encoding strict to match the spec, and stop skipping the `lenient`
      vectors
- [ ] Consider adding an API that takes bytes (`Uint8Array`)
